# TriAgent 架构说明（v1.0 RC）

> 配套文档：[evals/README.md](../evals/README.md)（评测口径与门禁）· [框架设计](agent/框架设计.md) · 红队评测报告

## 一、运行模型：确定性治理层与模型决策层的边界

TriAgent 的核心设计不是"更多 Agent"，而是**在确定性代码与模型自主性之间划出可验证的边界**：

```
用户请求
   │
   ▼
┌─────────────────────────────────────────────┐
│ 确定性治理层（不依赖 LLM，全部可单测）        │
│  鉴权(Sa-Token) · 演示只读拦截 · 每日额度     │
│  红旗状态机 · 工具权限矩阵 · 预算熔断 · 幂等  │
└─────────────────────────────────────────────┘
   │ 允许进入
   ▼
┌─────────────────────────────────────────────┐
│ 决策与执行层                                  │
│  Supervisor 规划 → AgentRegistry 路由        │
│  → 确定性分诊流 或 LLM 轮组装(DeepSeek 流式) │
│  → 全部工具调用经 ToolGateway 唯一入口       │
└─────────────────────────────────────────────┘
   │
   ▼
┌─────────────────────────────────────────────┐
│ 确定性验收与观测层                            │
│  输出护栏 · 审计 JSONL · DecisionLog 重放    │
│  OTel 风格 span 树（脱敏后可查）             │
└─────────────────────────────────────────────┘
```

**边界纪律**（面试讲解锚点）：

- 安全结论（EMERGENCY 短路、越权拒绝、预算熔断）**只由确定性代码做出**，模型输出永远不能推翻；
- LLM 只负责其擅长的部分：自然语言理解、报告解读文案、澄清话术组织；
- 治理层每个组件都是纯逻辑类（agent-core 不依赖 Spring AI/MyBatis/Redis），100% 单测覆盖。

## 二、核心组件与职责边界

| 组件 | 位置 | 职责 | 禁止承担 |
|---|---|---|---|
| AssistantOrchestrator | health-admin/agent | 组织一次轮次的阶段与状态迁移（薄编排器） | 不实现路由规则与安全判断 |
| AgentRegistry | health-admin/agent | 选择目标 Agent（连续性 + 冲突优先级） | 不调用模型或工具 |
| TriageDeterministicFlow | health-admin/agent | 红旗状态机多轮决策序列 | 不做任何 LLM 调用 |
| LlmTurnAssembler | health-admin/agent | 组装 LLM 轮上下文与流式回调 | 不决定最终安全结论 |
| TurnFinalizer | health-admin/agent | 组装对用户可见的最终结果 | 不重新执行工具 |
| ToolGateway | agent-core/tool | 权限→熔断→幂等→超时→审计唯一入口 | 不依赖提示词保证安全 |
| ToolAccessPolicy/Guard | agent-core/tool | 声明式角色→工具矩阵 + 真实拦截 | — |
| BudgetGuard | agent-core/tool | 单会话工具次数 + token 预算熔断 | 不静默降级为放行 |
| RequestTrace/Redactor | agent-core/trace | span 树记录 + 敏感字段脱敏 | 不记录明文密钥/身份证 |
| DemoAccessGuard/Quota | health-admin/security | 演示账号只读拦截 + 每日额度 | 不虚增被拒请求计数 |

## 三、关键决策记录

1. **为什么 agent-core 只依赖 spring-context + slf4j**：治理组件必须可以在没有数据库、没有模型的环境下被单测与重放。任何引入基础设施的诱惑都会让"确定性可验证"这个卖点失效。
2. **为什么拆编排器**：569 行的 Orchestrator 把路由、状态机、LLM 调用、结果组装揉在一起，无法独立测试；拆分后每个组件可用 150 例离线 harness 单独回归，重构门禁（通过率降幅 ≤2pp）才有意义。
3. **为什么评测不依赖真实模型**：150 例全部打在确定性组件上，CI 秒级出报告；真实模型质量由 30 例 golden set + LLM-as-Judge 离线专项承担。两套口径分离，成本可控且结论可复现。
4. **为什么演示账号是只读 + 额度**：公开环境的风险是匿名滥用与数据污染；写操作白名单只留 chat 与 logout，被拒请求不虚增额度计数（compareAndSet 循环保证语义正确）。
5. **Trace 为什么默认脱敏**：医疗场景的请求体可能携带真实症状与个人信息；span attributes 中的手机号/身份证/邮箱/JWT/密钥字段统一由 SensitiveRedactor 处理后才可经 /trace 查询。

## 四、评测体系（两套口径）

| 口径 | 数据集 | 对象 | 运行方式 | 用途 |
|---|---|---|---|---|
| 离线 harness | 150 版本化案例（6 维度） | 确定性治理与编排组件 | `mvn test -pl health-admin -Dtest=TriageEvalHarnessTest`，0 LLM 调用 | 重构门禁、CI 回归 |
| 在线质量 | 30 例 golden set | 端到端（含 DeepSeek） | 专项执行，LLM-as-Judge + 规则双轨 | 发布前质量结论 |
| 红队对抗 | 32 条断言（4 攻击维度） | 护栏与权限拦截 | 随 `mvn test` 进 CI | 安全闸门 |

**质量门禁**：离线通过率降幅 >2pp 阻断发布；任一 emergency/permission 案例失败即不通过（不允许按平均值掩盖）；红队断言全绿才可发布。

## 五、面试 15 分钟讲解路线

1. **0–2 分钟**：一句话定位（受治理的高风险 Agent Runtime）+ 首页演示；
2. **2–6 分钟**：确定性治理层与决策层边界（架构图 + ToolGateway 入口代码走读）；
3. **6–9 分钟**：评测体系（150 例离线 + 30 例在线 + 红队，一条命令复现）；
4. **9–12 分钟**：故障与降级（预算熔断 → DEGRADED 确定性指引、Redis 不可用时幂等兜底）；
5. **12–15 分钟**：取舍复盘（为什么不做诊断、为什么治理层不进 Spring、演示账号为什么不开放写权限）。
